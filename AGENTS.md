# Development

This repository runs nanocode agents durably on Vercel with [durable-harness](https://github.com/vercel-labs/durable-harness) (vercel.com/blog/making-every-harness-durable): each session is a Workflow SDK run whose event log holds every write nanocode makes, so a Function that dies mid-turn is replaced by another that rebuilds the session from the log and finishes the turn, as durable-harness does for Pi, OpenCode, fx, Claude Code and Codex. It is the third nanocode host after gakonst/nanocode-worker (Cloudflare Durable Objects) and the native CLI, and its job is to show where nanocode's abstractions fit a host they were not built for. Do not add code comments, README files, Cargo features, tests or test-only dependencies; the user maintains READMEs. TypeScript uses only erasable syntax and imports with `.ts` extensions, so Node 22.18 or newer runs `scripts/` directly and Next.js compiles the rest.

`vendor/nanocode-wasm/` is gakonst/nanocode-wasm's TypeScript host and compiled module at the revision `wasm-revision.json` records, with the SDK revision that package builds against and the module's size and SHA-256. The package is not on npm, Node refuses to strip types under `node_modules`, and a Vercel build cannot reach a `file:` sibling, so the repository carries it. `npm run vendor` refuses a sibling `../nanocode-wasm` (or `NANOCODE_WASM_DIR`) with uncommitted changes, runs its fingerprinted build and copies `src/*.ts`, both licenses and `dist/nanocode_wasm.wasm`. Change nanocode code in its own repositories, commit and push it there, then vendor.

## How a session is durable

`src/harness.ts` is a durable-harness kernel `Harness` (`durableAgent({ harness })`, the API durable-harness documents for writing your own) named `nanocode`. nanocode keeps its own durability: model step receipts, tool receipts with unknown outcomes after a crash, checkpoints, subagent journals and its turn log, all through the SDK's `SqlStore` and `SessionLog` over the package's `SqlHost`. A Workflow World is neither SQLite nor a linearizable key-value store, so `src/journal.ts` makes the run's event log nanocode's write-ahead log. Each drive replays the log's committed SQL batches, in order, into a `node:sqlite` `:memory:` database and serves nanocode from it. A transaction runs locally in `BEGIN IMMEDIATE`; one that changed `total_changes()` or `schema_version` is recorded, as `{kind, operation, statements}`, in a record-only kernel step `nanocode.sql` keyed `sql:<n>`, n counting the committed batches. A read or a no-op write is not recorded. One batch is in flight at a time and every transaction that runs meanwhile goes in the next one. The kernel's first writer wins each key and its epoch fence ignores a stale drive's steps, so the batches form one sequence whoever writes them; a batch whose output names another drive's writer is a `Restart`, a failed or refused batch poisons the journal and halts the drive, and the next drive rebuilds from the committed prefix. Replaying a recorded batch reproduces its effect because the SDK binds every value as a parameter and its SQL calls no time or random function; a batch that does not replay is `Fatal`.

`durability: "on"` (the default, durable-harness's Durable On) acknowledges a write as soon as it runs locally and waits for the log only at barriers: before a host tool runs, before a submission is placed, before the drive's `nanocode.settled:<n>` marker, and before nanocode's logged events reach the live stream. A crash then loses a suffix of acknowledged writes, never a gap, which is what nanocode would see had it crashed at the last durable write: model calls whose results are lost run again, and nothing outside the drive saw them, because tools and the live stream wait for the barrier. `durability: "strict"` acknowledges a write only once its batch is committed. The `durableAgent` itself runs `durability: "strict"`, so the kernel's own steps (placements, tools, markers) are durable before they return.

The kernel's inbox drives nanocode's. A drive places each pending submission by submitting it to nanocode's `TurnInbox` with the submission ID as its request ID, waiting for that write, and committing a `nanocode.place:<id>` step that places it; a crash between the two resubmits it, and nanocode answers `existing`. `steer` and `followUp` messages become queued turns, since the package cannot steer a running turn. The drive then runs nanocode's turns until none is pending and `settle` reports quiescence, disposes the runtime, writes the settled marker and sends `idle`. A delivery that finds no pending submission and a settled marker for the current batch count returns without opening nanocode, which every turn's backstop delivery does. The first drive records `nanocode.session`: a UUIDv7 session ID, as the SDK requires, and the provider, model and effort the session keeps when the app's defaults change. When the kernel aborts a drive (out of budget, preempted, halted) the harness disposes nanocode, whose writes then fail, and rethrows the kernel's reason.

Host tools are durable-harness `HostTool`s, offered to nanocode as `FunctionTool`s. A call runs as a kernel step `tool:<call_id>`, keyed by the call ID the package passes since gakonst/nanocode-wasm c043dfa, with the tool's own `replay` and its effect io, so durable-harness's tools work unchanged: `lib/agent.ts` gives the agent `workspaceTools(virtual())` from `durable-harness/tools`, a just-bash shell and file tools whose files are a document in the session's log, and `charge`, a `replay: "never"` stand-in for a payment that logs one line per charge. nanocode records its own receipt around each call and reports a call interrupted by a crash as an unknown outcome, so a `replay: "safe"` tool is not run again automatically: the model decides. `durable-harness/pi`'s `createCodingTools` needs Pi's packages installed even without Pi, so the repository uses the generic set.

Model requests go to the Vercel AI Gateway (`src/gateway.ts`). The package builds them without credentials; the host adds `Authorization: Bearer` and `x-api-key` with `AI_GATEWAY_API_KEY` or the Vercel OIDC token (`@vercel/oidc`, the deployment's token on Vercel, `VERCEL_OIDC_TOKEN` from `vercel env pull` locally) and refuses an endpoint outside `AI_GATEWAY_BASE_URL`'s origin. Claude sessions post to `/v1/messages` with Claude's own model IDs, which the gateway accepts. Codex sessions set the package's `gateway: "vercel"`, which uses the SDK's `ResponsesGateway::vercel()` and names models `openai/<model>` at `/v1`. `NANOCODE_PROVIDER` (`claude` or `codex`) and `NANOCODE_MODEL` choose a new session's model; Sonnet 5.5 and Luna by default. `NANOCODE_DURABILITY=strict` selects strict durability for the app's agent, and every drive logs its report (journal batches, transactions, reads, time waiting on batches, model requests and tool calls) as one `{"drive": …}` line, which `vercel logs --json` returns.

nanocode's logged events reach the session's live stream as durable-harness's vocabulary: `text` and `reasoning` deltas, `tool_start` and `tool_end`, `turn` with the result, `retrying`, `error` and `idle`. Each carries nanocode's `seq` and `request_id`. `src/reader.ts` replays a fold into a database and answers nanocode's `turn` and `page` reader commands without opening the session, for routes and scripts that need a turn's result or its full event log.

## The app

`lib/agent.ts` makes the one agent. `next.config.ts` wraps the config in `withDurableHarness(config, { agents: ["lib/agent.ts"] })`: without `agents` it imports every source file that calls `durableAgent(` into the flow route it generates, and `next build` then ran `scripts/drill.ts` while collecting page data. `app/api/chat/route.ts` is the agent's `chatRoute`: POST `{sessionId?, text}` streams the turn as server-sent events with `x-session-id`, and GET `?sessionId&cursor` resumes after the last event id. With `CHAT_TOKEN` set it requires `Authorization: Bearer <CHAT_TOKEN>`; without it the route is open under `next dev` and refuses every request in production, as durable-harness does. `app/api/chaos/route.ts`, enabled by `HARNESS_CHAOS=1`, arms durable-harness's process kill at the session's next tool call. The home page follows nanocode.xyz's (gakonst/nanocode-site 12cbb69, styled after commitmono.com): Commit Mono (`public/fonts/CommitMono-VF.woff2`, SIL OFL in `public/fonts/OFL.txt`) with `ss01`, `ss03`, `ss04` and `ss05` at 13px on a 17px line, `#111` on `#aaa` and the reverse in dark mode, a 24px two-line title, a fixed numbered navigation, inverted current, pressed and flickering focus states, and its chat box: a bordered transcript, a `›` prompt with an `ENTER` key, a dotted row of suggestions and a status line. `app/globals.css` holds those styles as plain CSS, since this app does not build with Zyzz. `app/page.tsx` renders per request, because whether it shows the token field and the crash button depends on `CHAT_TOKEN` and `HARNESS_CHAOS` at run time; `app/chat.tsx` keeps the session, transcript and cursor in `localStorage`, reconnects from the last event id when a stream drops, and shows the kernel's crash and takeover events in the transcript. nanocode's module is read from `vendor/nanocode-wasm/nanocode_wasm.wasm` under the working directory, a static path Next.js traces into both the chat and the flow route.

Run `npm ci`, `npm run check` and `npm run build`. `npm run dev` serves the app on world-local in `.workflow-data`. `npm run cli -- "prompt"` runs the same agent in one process on world-local and `npm run cli -- <session> ["prompt"]` continues or reattaches to a session; with a linked project, `node --env-file=.env.local` gives either the `VERCEL_OIDC_TOKEN` that `vercel link` or `vercel env pull` writes. The deployment is the Vercel project `tempoxyz/nanocode-vercel-durable`, linked by `vercel link --scope tempoxyz --project nanocode-vercel-durable`, with `CHAT_TOKEN` set for preview and production and `HARNESS_CHAOS=1` for preview only. `vercel deploy` makes a preview; `vercel.json` names the `nextjs` framework because a project created without one (`vercel project add`) fails the build with "No Output Directory named public". Vercel's World, queue and OIDC gateway credential need no other configuration, and durable-harness's generated `config.json` gives the flow route its queue trigger and `maxDuration: "max"`. Previews sit behind Vercel Authentication: open the page signed in to Vercel, and script requests with `vercel curl <path> --deployment <url> --scope tempoxyz -- <curl arguments>`, which creates the project's automation bypass secret on first use and sends it as `x-vercel-protection-bypass`. For self-hosting, `WORKFLOW_TARGET_WORLD=@workflow/world-postgres` with `WORKFLOW_POSTGRES_URL` moves sessions to Postgres. Vercel's Workflow limits apply per session: 10,000 steps, 25,000 events and 50 MB per step input (vercel.com/docs/workflows/pricing). Every cold drive folds the whole log and replays every SQL batch, so long sessions open more slowly; nothing snapshots the database yet.

## Measurements

`npm run drill [providers] [durabilities]` (default `claude,codex` and `on,strict`) runs nanocode with a scripted Anthropic or Responses model (`scripts/scripted.ts`) on world-local in `output/drill-<provider>-<durability>/`, in two processes. The first starts a session asking for a charge, and the drill SIGKILLs it halfway through the charge's 3 s confirmation. The second opens the same World, which re-enqueues the session; it finishes that turn and runs a second that writes and reads a file on the virtual workspace. The drill fails unless the ledger holds one charge, the killed process made one model request, the recovered one made three, the first of them carrying the charge as an unknown outcome, the charge step is recorded interrupted, both turns completed, the second read the file back, no request carried a credential, Codex requests named `openai/gpt-6-luna`, and the second turn's requests replayed the first turn's history. It writes `report.json` with timings, the World's event count, SQL batches and transactions by operation, the kernel's steps and each drive's journal statistics. `node scripts/mock-gateway.ts [port] [log]` serves the same scripted models over HTTP, so the app runs without a gateway credential: start it with any `AI_GATEWAY_API_KEY`, which it then requires, and run the app with that key and `AI_GATEWAY_BASE_URL=http://127.0.0.1:<port>`.

On 2026-10-20 on an Apple M1 Max with Node 22.23, two runs of each combination gave, for a session of one recovered turn and one workspace turn, 12 SQL batches for 48 Claude transactions and 49 Codex ones with Durable On against 48 and 49 strict, 65 World events against 173 and 176, recovery to the end of the first turn in 213–227 ms against 406–503 ms, and 298–411 ms against 471–660 ms for the workspace turn. Strict drives spent 62–76% of their time waiting on batches. Of the 48 Claude transactions, 26 were the SDK's `SessionLog` (18 event appends, 3 starts, 2 submits, 2 finishes, the schema) and 22 its `SqlStore` (14 replacements, 7 acquisitions, 1 peek). Killing the first process 10 ms after the charge began, while a batch's outcome was being written, instead left world-local with a step whose file says completed and an event log where it is still running: the next process waited 30 s on the dead writer's lock, the recovery's `step_retrying` was refused with `EntityConflictError` and swallowed, and the session yielded as contended every 2 s until the drill timed out. That is world-local's crash consistency, not this harness's, and the drill kills halfway through the confirmation, when no write is in flight. Through `next start` with `HARNESS_CHAOS=1` and the mock gateway, a process kill armed at the charge stopped the server mid-call; once restarted, a GET with the last cursor streamed the rest of the turn, the charge was logged once and the model was told its outcome was unknown.

With real models through the AI Gateway on 2026-10-20 (the project's OIDC token, from this laptop): Haiku 5.5 and Sonnet 5.5 answered through `/v1/messages` with nanocode's own request bodies and model IDs, and Luna answered through `/v1/responses` as `openai/gpt-6-luna`, calling `bash` and `read_file` on the virtual workspace. `npm run cli` asked Sonnet 5.5 for a charge, was SIGKILLed 2 s into its confirmation, and `npm run cli -- <session>` in a new process finished the turn: no second charge, and the model told the user the charge may have gone through and that it would not retry. On a preview in `tempoxyz`, a Sonnet 5.5 turn on Vercel's World answered through the chat route, and a process kill armed with `/api/chaos` 1.5 s into the charge ended its Function; the flow route's queue delivery re-announced the crash 1.6 s after it and finished the turn before the client reconnected 6 s after the kill, and the deployment's logs held one charge. Three turns in one preview session (a turn with `bash` and `read_file`, a turn with `bash`, and "Say done.") committed 14, 10 and 6 batches of 28, 20 and 15 transactions with Durable On, waiting 229–391 ms per batch, and drives took 8.7, 6.1 and 2.2 s; the same turns strict committed 30, 21 and 15 batches at 119–155 ms each and took 8.8, 7.0 and 3.3 s. Each kernel step costs two World writes, so on Vercel a strict turn spends its tool barriers, placements and markers plus about a third of a second for every one of nanocode's write transactions, and Durable On halves a session's steps against the 10,000-step limit.

## What this host taught the SDK

Done upstream for this repository:

- SDK a6bd38494: `FunctionTool` gives a host tool that returns a string a text output. It used to encode every value as JSON, so durable-harness's tools, which return text, reached the model as one escaped string literal.
- gakonst/nanocode-wasm c043dfa: `tools.call` receives `{ call_id }`, the stable key durable-harness, libfx (`executionId`) and the AI SDK (`toolCallId`) give their tools for idempotency, and `config.gateway: "vercel"` reaches the Vercel AI Gateway's Responses API with its model IDs. The package's Codex path had been built for provider-native endpoints behind the Worker's egress.

Open:

- nanocode's stores assume a SQL host or a linearizable key-value store. A World, Kafka, Redis streams or S3 conditional appends are logs: first writer wins per position, readers judge entries. `store-jsonl` already implements nanocode's fencing that way over one file; the same reader-judged protocol over an async append-and-read host would let the SDK keep its state in a World directly, without a local SQLite, statement text or replaying every batch on each drive.
- `TurnInbox` brings its own queue and event table. Here the kernel already has an inbox and a live stream, so 54% of nanocode's writes in the drill were its `SessionLog`, logged once in SQL and again as live events. A host with its own inbox needs `durable_prompt`, `durable_outcome`, `pending_turns` and an event callback without the log.
- Every interrupted host call is an unknown outcome. durable-harness, Pi and libfx let a tool declare it safe to run again; an SDK policy that redispatches an interrupted call of such a tool with the same call ID would let the kernel answer it from its own record.
- Model calls are invisible to the host: `dispatch` carries no call index or turn, so Agent Runs shows no model calls for nanocode and durable-harness's model crash drill cannot fire. Steering a running turn and stopping at the next step boundary before a known deadline (a Function's `maxDuration`, the kernel's budget) are missing from the package, so a budget yield cuts a model stream and repeats it.
- The package offers the `hands` tool to sessions that cannot have hands, and is not published, so hosts other than the Worker vendor it.
