# Development

This repository runs nanocode agents durably on Vercel with [durable-harness](https://github.com/vercel-labs/durable-harness) (vercel.com/blog/making-every-harness-durable): each session is a Workflow SDK run whose event log holds every write nanocode makes, so a Function that dies mid-turn is replaced by another that rebuilds the session from the log and finishes the turn, as durable-harness does for Pi, OpenCode, fx, Claude Code and Codex. It is the third nanocode host after gakonst/nanocode-worker (Cloudflare Durable Objects) and the native CLI, and its job is to show where nanocode's abstractions fit a host they were not built for. Do not add code comments, README files, Cargo features, tests or test-only dependencies; the user maintains READMEs. TypeScript uses only erasable syntax and imports with `.ts` extensions, so Node 22.18 or newer runs `scripts/` directly and Next.js compiles the rest.

The harness lives in gakonst/nanocode-ts as `nanocode-ts/vercel`, and this repository is the app around it: `package.json` names it as the git dependency `github:gakonst/nanocode-ts#<commit>`, which `package-lock.json` pins, and the package's committed `dist/` holds the compiled JavaScript and module, so installing it builds no Rust or TypeScript. Change the harness, the journal or the gateway in nanocode-ts, merge it there, then move the commit here with `npm install nanocode-ts@github:gakonst/nanocode-ts#<commit>`.

## How a session is durable

`nanocodeHarness` (nanocode-ts's `src/vercel/harness.ts`) is a durable-harness kernel `Harness` (`durableAgent({ harness })`, the API durable-harness documents for writing your own) named `nanocode`. nanocode keeps its own durability: model step receipts, tool receipts with unknown outcomes after a crash, checkpoints, subagent journals and its turn log, all through the SDK's `SqlStore` and `SessionLog` over the package's `SqlHost`. A Workflow World is neither SQLite nor a linearizable key-value store, so the adapter's `SqlJournal` (`src/vercel/journal.ts`) makes the run's event log nanocode's write-ahead log. Each drive replays the log's committed SQL batches, in order, into a `node:sqlite` `:memory:` database and serves nanocode from it. A transaction runs locally in `BEGIN IMMEDIATE`; one that changed `total_changes()` or `schema_version` is recorded, as `{kind, operation, statements}`, in a record-only kernel step `nanocode.sql` keyed `sql:<n>`, n counting the committed batches. A read or a no-op write is not recorded. One batch is in flight at a time, and every transaction that runs meanwhile, or in the same turn of the event loop, goes in the next one. The kernel's first writer wins each key and its epoch fence ignores a stale drive's steps, so the batches form one sequence whoever writes them; a batch whose output names another drive's writer is a `Restart`, a failed or refused batch poisons the journal and halts the drive, and the next drive rebuilds from the committed prefix. Replaying a recorded batch reproduces its effect because the SDK binds every value as a parameter and its SQL calls no time or random function; a batch that does not replay is `Fatal`.

`durability: "on"` (the default, durable-harness's Durable On) acknowledges a write as soon as it runs locally, and the app's `durableAgent` runs the kernel's run-ahead durability with it, so a batch, a placement, a tool step and the settled marker are written in order without waiting for the World. The kernel waits for everything written before a `replay: "never"` step starts and before the drive lets the session go, and a step that follows one the World did not accept is inert (its chain fence). A crash or a refused write then loses a suffix of the drive's writes, never a gap, which is what nanocode would see had it crashed at the last durable write: model calls whose results are lost run again, a `replay: "safe"` tool step is lost with the batch that admitted it, and a `never` tool runs only after nanocode's receipt for it is durable. Live events go to the session's stream as nanocode logs them, best effort, as every durable-harness harness sends its deltas, so after a crash a reader can see text that the resumed turn writes again. `durability: "strict"` acknowledges a write only once its batch is committed and runs the kernel strict, so every step is durable before it returns; `NANOCODE_DURABILITY=strict` selects it for the app.

The kernel's inbox drives nanocode's. A drive places each pending submission by submitting it to nanocode's `TurnInbox` with the submission ID as its request ID, waiting for that write, and committing a `nanocode.place:<id>` step that places it; a crash between the two resubmits it, and nanocode answers `existing`. `steer` and `followUp` messages become queued turns, since the package cannot steer a running turn. The drive then runs nanocode's turns until none is pending and `settle` reports quiescence, disposes the runtime, writes the settled marker and sends `idle`. A delivery that finds no pending submission and a settled marker for the current batch count returns without opening nanocode, which every turn's backstop delivery does. The first drive records `nanocode.session`: a UUIDv7 session ID, as the SDK requires, and the provider, model and effort the session keeps when the app's defaults change. When the kernel aborts a drive (out of budget, preempted, halted) the harness disposes nanocode, whose writes then fail, and rethrows the kernel's reason.

Host tools are durable-harness `HostTool`s, offered to nanocode as `FunctionTool`s. A call runs as a kernel step `tool:<call_id>`, keyed by the call ID the package passes since nanocode-ts c043dfa, with the tool's own `replay` and its effect io, so durable-harness's tools work unchanged: `lib/agent.ts` gives the agent `workspaceTools(virtual())` from `durable-harness/tools`, a just-bash shell and file tools whose files are a document in the session's log, and `charge`, a `replay: "never"` stand-in for a payment that logs one line per charge. nanocode records its own receipt around each call and reports a call interrupted by a crash as an unknown outcome, so a `replay: "safe"` tool is not run again automatically: the model decides. `durable-harness/pi`'s `createCodingTools` needs Pi's packages installed even without Pi, so the repository uses the generic set.

Model requests go to the Vercel AI Gateway (the adapter's `gatewayDispatch`). The package builds them without credentials; the host adds `Authorization: Bearer` and `x-api-key` with `AI_GATEWAY_API_KEY` or the Vercel OIDC token (`@vercel/oidc`, the deployment's token on Vercel, `VERCEL_OIDC_TOKEN` from `vercel env pull` locally) and refuses an endpoint outside `AI_GATEWAY_BASE_URL`'s origin. Claude sessions post to `/v1/messages` with Claude's own model IDs, which the gateway accepts. Codex sessions set the package's `gateway: "vercel"`, which uses the SDK's `ResponsesGateway::vercel()` and names models `openai/<model>` at `/v1`. A session's harness and model are fixed when it starts: a POST to `/api/chat` without a `sessionId` carries `{harness, model, effort, text}`, the route checks them against `lib/settings.ts` (the open-weight GLM-5.3, Kimi K3 and MiMo V2.6 Pro on the Codex harness, which SDK 3d983dea2's Vercel Responses gateway serves as `zai/glm-5.3`, `moonshotai/kimi-k3` and `xiaomi/mimo-v2.6-pro`, each with the reasoning efforts the SDK's `ModelCapabilities` allow, low, medium and high for GLM and MiMo and low and high for Kimi, and low when `effort` is absent) and answers 400 for any other, starts the session with `agent.sessions.start({ config: { nanocode: { provider, model, thinking } } })` and forwards the prompt to it, and the harness reads that entry into its `nanocode.session` effect, so every drive of the session opens the same backend and model. The effort can change during a session: a message whose whole text is `/effort <level>` is a command that nanocode-ts's harness (since ddff939) checks against the model, reports as an `effort` or `error` live event and applies to every later turn, so it is ordered and recovered with the prompts around it. A POST without `harness` and `model` starts the default pair at its default effort. `NANOCODE_PROVIDER` (`claude` or `codex`) and `NANOCODE_MODEL` choose the page's preselected pair and the model of sessions started without one, such as the CLI's; Codex with GLM-5.3 by default, and Sonnet 5.5 for `NANOCODE_PROVIDER=claude`. The picker lists only those open-weight models, as the public demo of open models: on 2026-10-20 each of them, and with the Claude harness Kimi K2.6 and K3, GLM-5.3 and its Flash, MiMo V2.6 Pro, DeepSeek V4 Flash and Pro, gpt-oss-120b, Qwen 3.8 27B and MiniMax M3 when the requests' model was rewritten on their way to the gateway, completed a turn calling `bash` and `read_file` and a follow-up, but the SDK's Claude backend refuses a model that is not a Claude model ("unsupported Claude routing model"), so the Claude harness has none to offer yet. `NANOCODE_DURABILITY=strict` selects strict durability for the app's agent, and every drive logs its report (journal batches, transactions, reads, time waiting on batches, model requests and tool calls) as one `{"drive": …}` line, which `vercel logs --json` returns.

nanocode's logged events reach the session's live stream as durable-harness's vocabulary: `text` and `reasoning` deltas, `tool_start` and `tool_end`, `turn` with the result, `retrying`, `error` and `idle`. Each carries nanocode's `seq` and `request_id`. `openReader` replays a fold into a database and answers nanocode's `turn` and `page` reader commands without opening the session, for routes and scripts that need a turn's result or its full event log.

## Measurements

`npm run drill [providers] [durabilities]` (default `claude,codex` and `on,strict`) runs nanocode with a scripted Anthropic or Responses model (`scripts/scripted.ts`) on world-local in `output/drill-<provider>-<durability>/`, in two processes. The first starts a session asking for a charge, and the drill SIGKILLs it halfway through the charge's 3 s confirmation. The second opens the same World, which re-enqueues the session; it finishes that turn and runs a second that writes and reads a file on the virtual workspace. The drill fails unless the ledger holds one charge, the killed process made one model request, the recovered one made three, the first of them carrying the charge as an unknown outcome, the charge step is recorded interrupted, both turns completed, the second read the file back, no request carried a credential, Codex requests named `openai/gpt-6-luna`, and the second turn's requests replayed the first turn's history. It writes `report.json` with timings, the World's event count, SQL batches and transactions by operation, the kernel's steps and each drive's journal statistics. `node scripts/mock-gateway.ts [port] [log]` serves the same scripted models over HTTP, so the app runs without a gateway credential: start it with any `AI_GATEWAY_API_KEY`, which it then requires, and run the app with that key and `AI_GATEWAY_BASE_URL=http://127.0.0.1:<port>`.

On 2026-10-20 on an Apple M1 Max with Node 22.23, two runs of each combination gave, for a session of one recovered turn and one workspace turn, 12 SQL batches for 48 Claude transactions and 49 Codex ones with Durable On against 48 and 49 strict, 65 World events against 173 and 176, recovery to the end of the first turn in 213–227 ms against 406–503 ms, and 298–411 ms against 471–660 ms for the workspace turn. Strict drives spent 62–76% of their time waiting on batches. Of the 48 Claude transactions, 26 were the SDK's `SessionLog` (18 event appends, 3 starts, 2 submits, 2 finishes, the schema) and 22 its `SqlStore` (14 replacements, 7 acquisitions, 1 peek). Killing the first process 10 ms after the charge began, while a batch's outcome was being written, instead left world-local with a step whose file says completed and an event log where it is still running: the next process waited 30 s on the dead writer's lock, the recovery's `step_retrying` was refused with `EntityConflictError` and swallowed, and the session yielded as contended every 2 s until the drill timed out. That is world-local's crash consistency, not this harness's, and the drill kills halfway through the confirmation, when no write is in flight. Through `next start` with `HARNESS_CHAOS=1` and the mock gateway, a process kill armed at the charge stopped the server mid-call; once restarted, a GET with the last cursor streamed the rest of the turn, the charge was logged once and the model was told its outcome was unknown.

With real models through the AI Gateway on 2026-10-20 (the project's OIDC token, from this laptop): Haiku 5.5 and Sonnet 5.5 answered through `/v1/messages` with nanocode's own request bodies and model IDs, and Luna answered through `/v1/responses` as `openai/gpt-6-luna`, calling `bash` and `read_file` on the virtual workspace. `npm run cli` asked Sonnet 5.5 for a charge, was SIGKILLed 2 s into its confirmation, and `npm run cli -- <session>` in a new process finished the turn: no second charge, and the model told the user the charge may have gone through and that it would not retry. On a preview in `tempoxyz`, a Sonnet 5.5 turn on Vercel's World answered through the chat route, and a process kill armed with `/api/chaos` 1.5 s into the charge ended its Function; the flow route's queue delivery re-announced the crash 1.6 s after it and finished the turn before the client reconnected 6 s after the kill, and the deployment's logs held one charge. The same drill on the public production deployment, from a client with no token, bypass or Vercel login, ended the same way with Haiku 5.5: the crash, the takeover, one charge in the logs, and a reply that the charge may have gone through and was not retried. Three turns in one preview session (a turn with `bash` and `read_file`, a turn with `bash`, and "Say done.") committed 14, 10 and 6 batches of 28, 20 and 15 transactions with Durable On, waiting 229–391 ms per batch, and drives took 8.7, 6.1 and 2.2 s; the same turns strict committed 30, 21 and 15 batches at 119–155 ms each and took 8.8, 7.0 and 3.3 s. Each kernel step costs two World writes, so on Vercel a strict turn spends its tool barriers, placements and markers plus about a third of a second for every one of nanocode's write transactions, and Durable On halves a session's steps against the 10,000-step limit.

Those drives still waited on the World at every barrier, and the page received nanocode's events only after their batch was durable, so text arrived with the turn's result. Since then Durable On runs the kernel's run-ahead durability, batches take every transaction of an event-loop turn, live events are not held for the batch, and the page returns its prompt at `idle` instead of at the stream's end, which a run-ahead drive's settle check delays by 250 ms or more. `node scripts/measure.ts <url> [rounds]`, with the app's base URL such as https://nanocode.xyz/vercel, posts three turns per session ("Say ok.", a turn with `bash` and `read_file`, "Say done.") and records when the response headers, the first text, the `turn` event, `idle` and the stream's end arrive, with `CHAT_TOKEN` and `VERCEL_AUTOMATION_BYPASS_SECRET` for previews. On 2026-10-20, four interleaved rounds from San Francisco against two previews in `iad1` with Sonnet 5.5, one before and one after, gave medians of 2.97 against 2.21 s to `idle` for the first turn, 5.26 against 3.74 s for the tool turn and 2.72 against 1.25 s for "Say done.", and first text at 2.77 against 2.00, 5.13 against 3.54 and 2.38 against 1.12 s. Drive reports after the change showed 0 to 5 ms replaying the log, 9 to 17 ms opening nanocode (197 ms on a cold instance) and model calls of 0.6 to 1.3 s with about 6,200 of their 6,400 input tokens read from the gateway's prompt cache, so a drive now takes its model time plus about 0.1 s. With `HARNESS_MARKS=1` the kernel writes timing marks to the live stream, which showed World writes acknowledged 50 to 190 ms after they were issued; its acknowledgment marks then trail the drive's `idle`, durable-harness's chat stream drops the settle check that `idle` started, and the stream never ends, so leave marks off for the chat route. On the public production deployment (Haiku 5.5), three rounds of the same script before and after measured the `turn` event at 3.52 against 1.57 s for the first turn, 4.19 against 2.36 s for the tool turn and 2.48 against 2.05 s for the follow-up.

Why replies looked unstreamed, measured on 2026-10-20 through `next start` on this laptop and the AI Gateway, with upstream chunks timed in `gatewayDispatch` and the page timed in headless Chromium (`output/sse-timeline.mjs`, `output/ui-timeline.mjs`): the page posted only finished paragraphs and dropped `reasoning` events, and the gateway's Anthropic stream holds text behind summarized thinking. Codex streams arrived steadily (Luna: 180 chunks, no gap over 400 ms after the first), and the chat route forwarded them in 50 ms batches (`event_coalesce_ms`). Claude turns that thought (nanocode sends `thinking: { type: "adaptive", display: "summarized" }`) paused 1.9–2.4 s (Haiku 5.5) and 2.2 s (Opus 5.5) after their first thinking deltas, then delivered the rest of the summary, its signature and the first 300–1,100 characters of text within 5 ms as 8–15 KB; Sonnet 5.5 and Haiku turns that did not think streamed steadily. Revealing a 15 KB burst at 1 − e^(−t/100 ms) finishes within half a second, while steady text trails the stream by about 100 ms: the largest frames of two Haiku replies were 69 and 276 characters, against 436 and 1,996 shown at once under reduced motion, and the largest frame of a Luna reply was 76.

## What this host taught the SDK

Done upstream for this repository:

- SDK a6bd38494: `FunctionTool` gives a host tool that returns a string a text output. It used to encode every value as JSON, so durable-harness's tools, which return text, reached the model as one escaped string literal.
- gakonst/nanocode-ts c043dfa (then nanocode-wasm): `tools.call` receives `{ call_id }`, the stable key durable-harness, libfx (`executionId`) and the AI SDK (`toolCallId`) give their tools for idempotency, and `config.gateway: "vercel"` reaches the Vercel AI Gateway's Responses API with its model IDs. The package's Codex path had been built for provider-native endpoints behind the Worker's egress.

Open:

- nanocode's stores assume a SQL host or a linearizable key-value store. A World, Kafka, Redis streams or S3 conditional appends are logs: first writer wins per position, readers judge entries. `store-jsonl` already implements nanocode's fencing that way over one file; the same reader-judged protocol over an async append-and-read host would let the SDK keep its state in a World directly, without a local SQLite, statement text or replaying every batch on each drive.
- `TurnInbox` brings its own queue and event table. Here the kernel already has an inbox and a live stream, so 54% of nanocode's writes in the drill were its `SessionLog`, logged once in SQL and again as live events. A host with its own inbox needs `durable_prompt`, `durable_outcome`, `pending_turns` and an event callback without the log.
- Every interrupted host call is an unknown outcome. durable-harness, Pi and libfx let a tool declare it safe to run again; an SDK policy that redispatches an interrupted call of such a tool with the same call ID would let the kernel answer it from its own record.
- Model calls are invisible to the host: `dispatch` carries no call index or turn, so Agent Runs shows no model calls for nanocode and durable-harness's model crash drill cannot fire. Steering a running turn and stopping at the next step boundary before a known deadline (a Function's `maxDuration`, the kernel's budget) are missing from the package, so a budget yield cuts a model stream and repeats it.
- The package offers the `hands` tool to sessions that cannot have hands.
