# Decisions

## How a session is durable

`Harness.create` (nanocode-ts's `src/vercel/Harness.ts`) is a durable-harness kernel `Harness` (`durableAgent({ harness })`, the API durable-harness documents for writing your own) named `nanocode`. nanocode keeps its own durability: model step receipts, tool receipts with unknown outcomes after a crash, checkpoints, subagent journals and its turn log, all through the SDK's `SqlStore` and `SessionLog` over the package's `SqlHost`. A Workflow World is neither SQLite nor a linearizable key-value store, so the adapter's journal (`Journal.create`, nanocode-ts's `src/vercel/Journal.ts`) makes the run's event log nanocode's write-ahead log. Each drive replays the log's committed SQL batches, in order, into a `node:sqlite` `:memory:` database and serves nanocode from it. A transaction runs locally in `BEGIN IMMEDIATE`; one that changed `total_changes()` or `schema_version` is recorded, as `{kind, operation, statements}`, in a record-only kernel step `nanocode.sql` keyed `sql:<n>`, n counting the committed batches. A read or a no-op write is not recorded. One batch is in flight at a time, and every transaction that runs meanwhile, or in the same turn of the event loop, goes in the next one. The kernel's first writer wins each key and its epoch fence ignores a stale drive's steps, so the batches form one sequence whoever writes them; a batch whose output names another drive's writer is a `Restart`, a failed or refused batch poisons the journal and halts the drive, and the next drive rebuilds from the committed prefix. Replaying a recorded batch reproduces its effect because the SDK binds every value as a parameter and its SQL calls no time or random function; a batch that does not replay is `Fatal`.

`durability: "on"` (the default, durable-harness's Durable On) acknowledges a write as soon as it runs locally. The kernel itself runs strict (nanocode-ts runs it run-ahead only with `runAhead: true`, which this app does not set), so each step is two World writes acknowledged in turn, and the drive writes batches, placements and the settled marker in order in the background where nothing waits for them. The kernel waits for everything written before a `replay: "never"` step starts and before the drive lets the session go, and a step that follows one the World did not accept is inert (its chain fence). A crash or a refused write then loses a suffix of the drive's writes, never a gap, which is what nanocode would see had it crashed at the last durable write: model calls whose results are lost run again, a `replay: "safe"` tool step is lost with the batch that admitted it, and a `never` tool runs only after nanocode's receipt for it is durable. Live events go to the session's stream as nanocode logs them, best effort, as every durable-harness harness sends its deltas, so after a crash a reader can see text that the resumed turn writes again. `durability: "strict"` acknowledges a write only once its batch is committed and runs the kernel strict, so every step is durable before it returns; `NANOCODE_DURABILITY=strict` selects it for the app.

The kernel's inbox drives nanocode's. A drive places each pending submission by submitting it to nanocode's `TurnInbox` with the submission ID as its request ID and, once that write is durable, committing a `nanocode.place:<id>` step that places it; a crash between the two resubmits it, and nanocode answers `existing`. Since nanocode-ts 01232e8 the placement commits in the background while the turn's model request runs, and the drive awaits every placement before it reads the pending submissions again. A `steer` message that arrives while a turn runs steers it (nanocode-ts e79b665): the drive watches for submissions during the turn, steers each into it with its submission ID, which the SDK accepts once, records the placement and sends `steered`; the SDK hands a steer to the model at its next call, so a reply being streamed finishes first and the answer to the steer follows as a new message. A steer no running turn takes, and every `followUp`, becomes a queued turn. The drive then runs nanocode's turns until none is pending and `settle` reports quiescence, disposes the runtime, writes the settled marker and sends `idle`. A delivery that finds no pending submission and a settled marker for the current batch count returns without opening nanocode, which every turn's backstop delivery does. The first drive records `nanocode.session`: a UUIDv7 session ID, as the SDK requires, and the provider, model and effort the session keeps when the app's defaults change. When the kernel aborts a drive (out of budget, preempted, halted) the harness disposes nanocode, whose writes then fail, and rethrows the kernel's reason.

Host tools are durable-harness `HostTool`s, offered to nanocode as `FunctionTool`s. A call runs as a kernel step `tool:<call_id>`, keyed by the call ID the package passes since nanocode-ts c043dfa, with the tool's own `replay` and its effect io, so durable-harness's tools work unchanged: `lib/agent.ts` gives the agent `charge` alone, and nanocode-ts's harness adds the workspace: a bash on `SqlFileSystem` at `/workspace`, whose files are rows of the session's journaled SQLite, behind the SDK's own workspace tools (Claude's `Bash`/`Read`/`Edit`/`Write`, Codex's `apply_patch`/`exec_command`) and Code Mode's `bash`. `charge` is a `replay: "never"` stand-in for a payment that logs one line per charge. nanocode records its own receipt around each call and reports a call interrupted by a crash as an unknown outcome, so a `replay: "safe"` tool is not run again automatically: the model decides. `durable-harness/pi`'s `createCodingTools` needs Pi's packages installed even without Pi, so the repository uses the generic set. Since nanocode-ts build-de5fd83 the agent runs in Code Mode (`nanocodeHarness({ codeMode: true, fetch })`): the model writes `exec` scripts that call these tools as `tools.bash()`, `tools.write_file()` and so on, each call still a `tool:<call_id>` step, and `fetch` inside scripts is `offline`, which refuses every request, so the public deployment is not an open proxy. A cell runs in a QuickJS context in the drive's process (since nanocode-ts build-d5bbbb2) and does not outlive the drive. On 2026-10-22 with build-d5bbbb2, `npm run cli` with Haiku 5.5 wrote a file, ran `bash` and left an un-awaited fetch in one QuickJS cell, and the drive settled in 4.1 s; on in-realm cells an un-awaited fetch had ended a Node process. On 2026-10-22 `npm run cli` with Haiku 5.5 wrote a file, ran `bash` on it and caught the refused fetch in one cell, in two model requests and 3.0 s.

Model requests go to the Vercel AI Gateway (the adapter's `Gateway.dispatch`). The package builds them without credentials; the host adds `Authorization: Bearer` and `x-api-key` with `AI_GATEWAY_API_KEY` or the Vercel OIDC token (`@vercel/oidc`, the deployment's token on Vercel, `VERCEL_OIDC_TOKEN` from `vercel env pull` locally) and refuses an endpoint outside `AI_GATEWAY_BASE_URL`'s origin. Claude sessions post to `/v1/messages` with Claude's own model IDs, which the gateway accepts. Codex sessions set the package's `gateway: "vercel"`, which uses the SDK's `ResponsesGateway::vercel()` and names models `openai/<model>` at `/v1`. A session's harness and model are fixed when it starts: a POST to `/api/chat` without a `sessionId` carries `{harness, model, effort, text}`, the route checks them against `lib/settings.ts` (Claude Haiku and Sonnet 5.5 and the open-weight GLM-5.3 and Kimi K3 as `zai/glm-5.3` and `moonshotai/kimi-k3` on the Claude harness, and GPT-6 Luna, GPT-6.1 Sol and the open-weight GLM-5.3 and Kimi K3 on the Codex harness, which SDK 3d983dea2's Vercel Responses gateway serves as `zai/glm-5.3` and `moonshotai/kimi-k3`, each with the reasoning efforts the SDK's `ModelCapabilities` allow and its default when `effort` is absent, which `lib/settings.ts` reads from `nanocode-ts/models`, the catalog the module reports, together with each model's name and whether it takes the priority tier, keeping only the labels, the allowlist and the Claude-harness open models, which the catalog does not list, as its own) and answers 400 for any other, starts the session with `agent.sessions.start({ config: { nanocode: { provider, model, thinking } } })` and forwards the prompt to it, and the harness reads that entry into its `nanocode.session` effect, so every drive of the session opens the same backend and model. The effort can change during a session: a message whose whole text is `/effort <level>` is a command that nanocode-ts's harness (since ddff939) checks against the model, reports as an `effort` or `error` live event and applies to every later turn, so it is ordered and recovered with the prompts around it. A POST without `harness` and `model` starts the default pair at its default effort. `NANOCODE_PROVIDER` (`claude` or `codex`) and `NANOCODE_MODEL` choose the page's preselected pair and the model of sessions started without one, such as the CLI's; Claude with Haiku 5.5 by default, and Luna for `NANOCODE_PROVIDER=codex`, both at low effort. The open-weight models are the point of the demo, the Claude and Codex models the cheaper two of each harness: on 2026-10-20 GLM-5.3, Kimi K3 and MiMo V2.6 Pro on the Codex harness, and with the Claude harness Kimi K2.6 and K3, GLM-5.3 and its Flash, MiMo V2.6 Pro, DeepSeek V4 Flash and Pro, gpt-oss-120b, Qwen 3.8 27B and MiniMax M3 when the requests' model was rewritten on their way to the gateway, completed a turn calling `bash` and `read_file` and a follow-up, and since SDK f96a9a0d7 and nanocode-ts dc7f502 the Claude backend takes any model ID, so the Claude harness offers GLM-5.3 and Kimi K3 under the gateway's slugs, which completed turns calling `bash` and `read_file` that day. The SDK knows no output limit for them, so each carries `maxTokens` in `lib/settings.ts`, which the route passes as the session's `max_tokens`: the Vercel AI Gateway's model catalog (`/v1/models`) listed 1,000,000 for GLM-5.3 and 131,072 for Kimi K3 on 2026-10-21. Before, the backend refused them as "unsupported Claude routing model". Luna and Sol carry `serviceTier: "priority"`, which the route passes as the session's `service_tier` (nanocode-ts a5aa761), and `lib/agent.ts` leaves subagents on, as nanocode-ts's `App.create` does by default, so the model gets the workspace, charge and subagent tools inside Code Mode. Measured from San Francisco through nanocode.xyz/vercel on 2026-10-21 with `output/ttft/api.mjs` (four rounds each, the functions in iad1), a Luna session started on the first keystroke showed its first text after a median 1,339 ms instead of 1,804 and a Haiku follow-up after 1,210 ms instead of 1,408; requests straight to the AI Gateway from the same place put Luna's first text at 792 ms on the priority tier and Haiku's at 769 ms. Most of the rest passes before the response headers, 250 to 600 ms in which durable-harness's `chatRoute` calls the World's `liveEnd` and `send` in turn, and in the Workflow stream between the drive and the route. Both are durable-harness's: vercel-labs/durable-harness#22 asks for `liveEnd` to stop preceding `send`, and #23 for an inline drive to hand its live events to the reader in the same invocation instead of through the World. `NANOCODE_DURABILITY=strict` selects strict durability for the app's agent, and every drive logs its report (journal batches, transactions, reads, time waiting on batches, model requests and tool calls) as one `{"drive": …}` line, which `vercel logs --json` returns.

nanocode's logged events reach the session's live stream as durable-harness's vocabulary: `text` and `reasoning` deltas, `tool_start` and `tool_end`, `turn` with the result, `retrying`, `error` and `idle`. Each carries nanocode's `seq` and `request_id`. `Reader.open` replays a fold into a database and answers nanocode's `turn` and `page` reader commands without opening the session, for routes and scripts that need a turn's result or its full event log.

## The app

`lib/agent.ts` makes the one agent. `next.config.ts` wraps the config in `withDurableHarness(config, { agents: ["lib/agent.ts"] })`: without `agents` it imports every source file that calls `durableAgent(` into the flow route it generates, and `next build` then ran `scripts/drill.ts` while collecting page data. `app/api/chat/route.ts` is one line, `export const { GET, POST } = nanocode`, where `nanocode` is `App.create` from `nanocode-ts/vercel` in `lib/agent.ts` (the agent's `chatRoute` plus session starts, and `app/api/chaos/route.ts` is `nanocode.chaos`): POST `{sessionId?, text}` streams the turn as server-sent events with `x-session-id`, POST `{warm: true, harness, model, effort}` starts a session without a prompt and answers `{sessionId}`, which the page sends at the first keystroke of a prompt in a new session so the session and a warm Function exist before Enter, and GET `?sessionId&cursor` resumes after the last event id. ## Measurements

The first starts a session asking for a charge, and the drill SIGKILLs it halfway through the charge's 3 s confirmation. ## What this host taught the SDK

Done upstream for this repository:

- SDK a6bd38494: `FunctionTool` gives a host tool that returns a string a text output. It used to encode every value as JSON, so durable-harness's tools, which return text, reached the model as one escaped string literal.
- nanocodexyz/nanocode-ts c043dfa (then nanocode-wasm): `tools.call` receives `{ call_id }`, the stable key durable-harness, libfx (`executionId`) and the AI SDK (`toolCallId`) give their tools for idempotency, and `config.gateway: "vercel"` reaches the Vercel AI Gateway's Responses API with its model IDs. The package's Codex path had been built for provider-native endpoints behind the Worker's egress.

Open:

- nanocode's stores assume a SQL host or a linearizable key-value store. A World, Kafka, Redis streams or S3 conditional appends are logs: first writer wins per position, readers judge entries. `store-jsonl` already implements nanocode's fencing that way over one file; the same reader-judged protocol over an async append-and-read host would let the SDK keep its state in a World directly, without a local SQLite, statement text or replaying every batch on each drive.
- `TurnInbox` brings its own queue and event table. Here the kernel already has an inbox and a live stream, so 54% of nanocode's writes in the drill were its `SessionLog`, logged once in SQL and again as live events. A host with its own inbox needs `durable_prompt`, `durable_outcome`, `pending_turns` and an event callback without the log.
- Every interrupted host call is an unknown outcome. durable-harness, Pi and libfx let a tool declare it safe to run again; an SDK policy that redispatches an interrupted call of such a tool with the same call ID would let the kernel answer it from its own record.
- Model calls are invisible to the host: `dispatch` carries no call index or turn, so Agent Runs shows no model calls for nanocode and durable-harness's model crash drill cannot fire. Steering a running turn and stopping at the next step boundary before a known deadline (a Function's `maxDuration`, the kernel's budget) are missing from the package, so a budget yield cuts a model stream and repeats it.
- The package offers the `hands` tool to sessions that cannot have hands.
